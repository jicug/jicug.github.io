### 発表①：IBM watsonx Code AssistantによるIBMクラウドへのアプリ移植（鹿野氏）

#### 概要・背景

- 生成AIで作成したアプリをローカルで動かすだけでなく、Webサーバー・アプリサーバー・DBサーバーの三層インフラへデプロイすることを目指した
- 前回まで仮想サーバー上にコンテナを立てて動かしていたアプリを、サーバーレス環境（IBMクラウド Code Engine・Object Storage）へ移植する作業をBobに実施させた

#### IBM watsonx Code Assistant（Bob）バージョン2.0へのアップデート

- 複数タスクを並列処理するサブエージェント機能が追加
- エージェント作業中に追加指示が可能になった
- GUIベースのMCPサーバー連携機能が公式に追加（未検証）

#### デプロイ方式の選定

- Bobに移植方式を質問したところ、①MCPサーバー自作、②Terraform、③CLIコマンドラインの3択が提示された
- MCPサーバー自作は難易度が高く、バグや作り直しリスクがあるため今回は見送り
- Terraformは前回実施済みで習得コストが高いことが判明していたため、今回はCLIコマンドラインを選択

#### Bobを使った開発・デプロイの流れ

- 人間が要件定義を作成し、Bobに渡して「追加の質問があるか」を確認させる（リージョン指定・既存リソースの有無など）
- Bobが詳細な設計書・デプロイ計画書（マークダウン形式）を自動生成（コスト見積もり・運用上の注意事項も含む）
- フェーズごとに作業を進め、人間の承認が必要な箇所では確認を求めてくる
- コマンド実行に失敗した場合は自律的に別の方法で再試行する
- 一部（Object StorageのパブリックアクセスON設定など）はポータルでの手動操作が必要だった
- Windowsのプロセスモニターでサブエージェントが複数並列動作していることを確認

#### 成果・所感

- アプリ開発からクラウドデプロイまで約3〜4日で完了（通常は8週間程度かかる作業）
- CLIコマンドラインだけでもデプロイが可能であり、AI時代においてTerraformだけが選択肢ではないと感じた
- ただしTerraformは再現性が高く確実であるのに対し、AIによるデプロイは毎回同じ結果になるとは限らない点に注意が必要
- ドキュメント生成能力が高く、要件定義から詳細設計書・操作手順書・効果音の割り当てまで自動生成した

#### デモ：マルチプレイゲームの公開

- 今回作成したマルチプレイゲーム（Node.js + JavaScript）をIBMクラウド（Code Engine + Object Storage）上に無料枠でデプロイ
- 参加者がプレイヤー画面にアクセスし、チーム対抗でゲームを実施（Aチーム296点 vs Bチーム287点、Aチームの勝利）
- ゲームのスコアや参加者数などをカスタムメトリクスとしてオブザーバビリティツール（IBM Instana）に記録していく予定

### 発表②：BobIDEで継続的に知見を残し、経緯を引き継いで開発し続ける仕掛け（田中氏）

#### 自己紹介

- フリーランスとして2004年より活動。フロントエンド開発をベースに生成AI・IoT・XRを取り入れた開発を行っている

#### 経緯・知見を残す仕組み（Docs Structure）

- セッションをまたぐとAIが過去の文脈を忘れてしまう問題に対処するため、独自の経緯管理システムを導入
- 「申し送り（Docs Letter）」と「知見ノート」をAIに書かせ、Gitにコミットして蓄積する
- セッション終了時にワンショットのマークダウン指示を与えることで、申し送り作成・コミット・次セッションへの引き継ぎを自動化
- 知見ノートには開発の進捗だけでなく、トラブルシューティングの内容も記録される
- この仕組みはGitHubで公開している「AIとコラボレーションするパターン集」の一つとして公開済み

#### Bobコイン（トークン）消費が増えるケース

- プロトタイプ開発の初手で議論を広げながら実装する場合（仕様が固まるまで時間がかかる）
- 過去の開発で意思決定が揺れた箇所を再開する際にAIが迷う場合
- 実装パートが終わっていないのに次の設計検討を同時に行う場合
- AIの状況把握がずれており、ユーザーとの軌道修正の議論が頻発する場合

#### Bobコイン消費を抑えるための工夫

- 経緯ノートのフォルダ全体を探索させず、人間が記憶をもとに「このファイルを見てください」と明示的に指定する
- 実装箇所・グレップのキーワードを明示してから実装を開始させる
- 実装計画も人間側から明示して渡す（マイクロマネジメント的ではあるが効果的）
- ライブラリのインストールやコマンド実行など、人間がやれる作業は人間が行う
- AIが考える量を減らし、次の対応だけをさせる

#### セキュリティ管理の仕組み

- AIが機密情報（パスワード等）をGitにコミットしてしまうリスクに対処するため、以下のツールを併用
  - **secretlint**：機密情報の自動チェック
  - **gitleaks**：機密情報の自動チェック（二重チェック）
  - **pre-commit**：コミット時に自動でチェックが走る仕組み
- AIへの指示だけでは確実性が低くトークンも消費するため、従来型のプログラム的な仕組みで補完することが重要
- Bobへのコミット指示にも「プッシュはしないでください」「機密情報を含めないでください」などのルールをマークダウンで明示している

#### スキルズ・モード設定に関する所感（鹿野氏との対話）

- Bobのスキルズ機能やモード設定は発動タイミングが不明確なため、両氏ともあまり活用していない
- マークダウンファイルにガードレールとなる指示をまとめ、必要なタイミングでワンショットで渡す方式が使いやすい
- MCPサーバーについては、Playwright（ブラウザ操作）を試したことがある程度で、IBMクラウド公式のMCPサーバーは現時点では見当たらない

## 鹿野さん発表：IBM Bobを使ったIBMクラウドへのアプリ移植

### 発表概要と自己紹介・前回までの振り返り

- 発表者鹿野さんは某社に勤務し、データセンターやマルチクラウド・ハイブリッドクラウド環境の構築・運用・サービス提供を担当している。
- 今回のテーマは、仮想サーバー上で動作していたマルチプレイゲームアプリをIBMクラウドのサーバーレス環境（コードエンジン＋オブジェクトストレージ）へAIで移植することである。
- 前回まではLinux仮想サーバー上にWebサーバー・アプリサーバー・DBサーバーの三層構成を構築し、フラッシュクイズアプリとオブザーバビリティ監視ツールを作成した。
- AIを使うことで、通常8週間かかるインフラ構築とアプリ開発が約2日間で完了するというすばらしい効率化が実証された。
- 今回の移植対象はNode.jsバックエンドとJavaScriptフロントエンドで構成されるマルチプレイゲームで、コマンドラインのみを使ってデプロイする方式を採用した。
- 6月に試したTerraformは学習コストが高いという知見を踏まえ、今回はよりシンプルなCLI（コマンドライン）方式を選択している。

### IBM Bobによる移植作業の手順と実演・成果

- IBM Bobはバージョン2.0にアップデートされ、サブエージェントによる並行タスク処理、作業中の追加指示、GUIベースのMCPサーバー対応などが強化された。
- 移植作業はまず要件定義をBobに渡し、Bobから不足情報（リージョン、既存リソースの有無など）を質問させてから計画書を作成させる手順を採用した。
- Bobが生成したデプロイ計画書にはアーキテクチャ概要・フェーズ別手順・変数一覧・コスト見積もり・運用上の注意事項が自動で含まれており、ドキュメント品質が高い点が評価された。
- 作業中にBobは失敗を自己検知して別の方法で自動修復しながら進めるが、IBMクラウドポータルでのパブリックアクセス設定など一部手動操作が必要な場面もあった。
- 移植完了後、参加者全員がゲームにアクセスしてチーム対抗戦（Aチーム296点 vs Bチーム287点）を実施し、ゲームが正常動作することを確認した。
- 参加者の点数や人数などのメトリクスはオブザーバビリティ（IBMインスターナー）に記録される仕組みで、デジタルマーケティング分析に活用できることが説明された。
- 今後はTerraformも有力な選択肢だがAI時代ではCLIも十分機能すること、MCPサーバーの活用やインスターナーとの連携も検討していると述べた。



## 田中正吾氏発表：IBM BobIDEで知見・経緯を残して開発し続ける仕組み

### セッション間の忘却対策と経緯管理システム（Docs Structure）

- 発表者田中正吾氏はIBMチャンピオンであり、屋号ワンフットシーバス代表として2004年からフリーランスでフロントエンド開発・生成AI・IoT・XRを手がけている。
- IBM Bobはトークン上限（現在最大1MB程度）があり、セッションをまたぐと過去の経緯を忘れるため、申し送り（Docs Letter）と知見ノートをAIに書かせる「経緯管理システム（Docs Structure）」を導入している。
- セッション終了時にワンショットの指示（マークダウン形式）を入力するだけで、申し送り・知見ノート作成・Gitコミットを自動で実施させる仕組みが構築されている。
- 知見ノートにはブートストラップ導入・カードレイアウト実装・Bobコイン急増の原因調査など開発上の重要ポイントやトラブルシューティングが蓄積されていく。
- この仕組みはGitHubで公開している「AIとコラボレーションするパターン集」の一つ「Docs Structure」として公開されており、ワンショットインストーラーも用意している。
- 経緯があることで次セッション開始時に「この資料をもとに進めて」と強い文脈を与えられ、人間が口頭で過去を説明する手間が大幅に削減できる。

### Bobコイン消費の傾向分析とトークン節約の工夫・セキュリティ対策

- Bobコインの消費が増えるケースとして、プロトタイプ開発初手での議論の膨らみ、曖昧な経緯による方針の揺れ、実装パート終了後すぐに別タスクへ移行する場面、AIとの頻繁な軌道修正議論などが挙げられた。
- コイン消費を抑えるには、人間が明示的に焦点を絞って指示し、フォルダ全体を探索させず「この資料を見て」と狙い打ちで指示することが有効である。
- IBM Bobはモデルを自動選択しており（ClaudeやGraniteなど）制御は難しいため、コイン節約にはモデル制御よりも明快な指示の磨き込みが重要と結論付けた。
- セキュリティ対策としてsecretlintとgitleaksをダブルで導入し、コミット時に機密情報が混入しないようプレコミットフックで自動チェックする仕組みを構築している。
- AIに全てのセキュリティチェックを任せると毎回同じ動作にならずトークンも多消費するため、確実に動く従来型プログラムの仕組みと併用することがトークン節約に効果的である。
- スキルズよりもマークダウンによるワンショット指示を好む理由として、スキルズは発動タイミングが不明確で予期しない縛りが発生することがあり、マークダウンのほうが視認性・制御性ともに高いためである。



## 質疑応答・Bob IDE機能の意見交換

- 鹿野さんからBobの設定画面（モード・MCP・スキルズ）について質問があり、田中氏はスキルズよりマークダウンのワンショット指示を主に使っていると回答した。
- IBM Bobのプランモードは「計画できたので開発します」と勝手に進もうとするため、「ノートに書いて報告しろ」と明示的に止める使い方が有効であると共有された。
- MCP連携についてはPlaywrightを使ったブラウザ操作・画面チェックを試したが、E2Eチェックはトークン消費が大きいためAPIやモンキーテストのほうが確実との見解が示された。
- IBMクラウド操作用のMCPサーバーが公式に存在しないため、ドキュメント・APIリスト・関数リストをまとめたMCPを自作して仕様伝達コストを減らす方法が紹介された。
- IBM BobのUI上の「エディター設定」や「スタートワークフロー」など未探索の機能が複数あり、今後試してみたいという意見が出た。
- 言語設定で日本語が選択可能であることが画面共有中に発見され、AIが意気揚々と英語で話し出す問題への対策として活用できる可能性が示唆された。
